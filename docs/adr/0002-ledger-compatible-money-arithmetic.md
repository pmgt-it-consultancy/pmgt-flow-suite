# Preserve ledger-compatible arithmetic in the Kotlin port and reconcile totals on the server

The Kotlin rewrite of the Android POS will reproduce the existing money arithmetic exactly rather than improve it. The Kotlin implementation uses IEEE-754 double-precision values and replicates `roundMoney` — `Math.round((amount + Number.EPSILON) * 100) / 100` — including the epsilon term, together with the `normalizeVatRate` behaviour that accepts a VAT rate expressed as either `12` or `0.12`. `BigDecimal` is explicitly rejected for this port. Alongside it, the Convex backend gains Totals Reconciliation: on sync push it recomputes an Order Aggregate's money figures from its items and compares them against the Device-Computed Totals the tablet sent, recording a Totals Divergence when they disagree.

Bit-for-bit compatibility is chosen over arithmetic accuracy because the arithmetic is already in production. Three live stores have settled Business Days whose Z-Reports, VAT breakdowns and SC/PWD exemptions were produced by the existing implementation. A `BigDecimal` port would be more accurate on the fractional cases and therefore divergent: identical inputs would yield a different centavo on some orders, historical reports would cease to be reproducible, and a reconciliation between a device and the server would report differences that reflect the port rather than any defect. Ledger-Compatible Arithmetic is the constraint; accuracy is not. A future move to decimal arithmetic remains available as a deliberate money-model change carrying its own migration for historical orders, and must not happen as a side effect of a language port. The Kotlin source states this in a comment at the rounding function so that a later reader does not correct it.

Totals Reconciliation exists because the tablet is currently the sole authority on money. Sync push assigns `grossSales`, `vatAmount` and `netSales` directly from the pushed row onto the order without recomputation, while the backend already recomputes totals for its own mutations in `orders.ts`, `discounts.ts` and `helpers/voidsHelpers.ts`, and `checkout.ts` validates payments against the stored `order.netSales` rather than deriving it. The reference implementation therefore sits in a part of the system this migration does not rewrite, and applying it to pushed rows costs no new arithmetic. Reconciliation flags and accepts; it never rejects. A Totals Divergence must not block a sale, strand a synced order, or make a tablet unable to push, because the cashier cannot act on an arithmetic disagreement mid-service. The same mechanism closes an existing gap in the push path that bypasses the payment guard enforced by `processPaymentCore`.

Relocating the money calculations to the server was considered and rejected: the POS must total an order with no network, so the device must compute. Generating both implementations from a shared specification was also rejected as disproportionate ceremony for seven small functions, given that reconciliation already provides drift detection; it becomes worth revisiting only if divergences are observed in practice.

Correctness of the port is established by golden vectors drawn from real orders at the three live stores rather than from hand-written cases alone. Those orders already encode the VAT, SC/PWD, split-payment and void combinations that actually occur, together with the results the existing implementation produced, so replaying them through the Kotlin implementation tests the shapes the business generates rather than the shapes an author imagined. The exported fixture carries order amounts only, without customer or payment-instrument detail.

This decision is reversed only by an explicit choice to change the money model itself, which would require migrating or annotating historical orders so that settled Business Days remain interpretable. Sustained Totals Divergence in production is the signal that the port has drifted, not that this decision was wrong.
